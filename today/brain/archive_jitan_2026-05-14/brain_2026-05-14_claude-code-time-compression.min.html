「AI に任せるべきタスク」の判断フロー

・ 判断基準 1: そのタスクは「再現可能な手順」を書けるか

手順が書ければ、AI に任せられる。手順が書けないタスク(クリエイティブ判断・人間関係の調整など)は任せない。

・ 判断基準 2: そのタスクは週 30 分以上かかってるか

週 30 分以下の単発タスクは、Claude Code に投げる設定時間の方がコスト高くなる。週 30 分以上か、月 4 回以上発生するタスクから優先する。

失敗しても自分で巻き戻せるタスク(下書き生成・ファイル整形など)は安全。失敗が即クライアントに届くタスク(納品メッセージ・送信ボタン)は最初から AI に任せない。

工程 1: 提案資料生成 — 3 時間 → 15 分

提案資料(クライアントへの企画書・ピッチ資料・営業資料など)を 1 本作るのに、Claude Code 導入前は 3 時間かかってた。導入後は 15 分。

圧縮前の状況

当時の作業手順:

① 案件詳細を読む(15 分)

② Claude のブラウザ版で骨子を生成(20 分)

③ 骨子を Google Docs に貼って、見出しを整える(30 分)

④ 各見出しの本文を Claude で生成(45 分)

⑤ 生成された本文を案件主の業界に合うよう修正(60 分)

⑥ スライド化(Google Slides で手動)(30 分)

合計 200 分(3 時間 20 分)。

問題は「⑤ 修正」と「⑥ スライド化」が手動だったこと。生成された本文をひたすら読み直して、案件主の業界用語に書き換える。Google Slides で 1 枚ずつ手動でスライド化。これが時間泥棒だった。

圧縮後の手順

Claude Code + Claude Design の組み合わせで以下になった:

① 案件詳細を Claude Code に貼る(2 分)

② 提案資料生成プロンプトを実行(5 分・Claude が骨子 + 本文を一気に生成)

③ 出力結果を Claude Design に渡してスライド化(5 分・自動)

④ Claude Design でスライドを微調整(3 分)

合計 15 分。

「修正」と「スライド化」を Claude Code と Claude Design に任せたら、3 時間 → 15 分になった。

提案資料生成プロンプト全文

Claude Code に投げてるプロンプトはこれ。コピペで使える。

あなたは案件主向けの提案資料を作成する補助アシスタントです。

以下の案件詳細から、提案資料の骨子と本文を作成してください。

--- 案件詳細 ---
[案件詳細を貼り付け]

--- 案件主の業界・企業情報 ---
[業界 / 企業規模 / 過去の発信から推測した文化 を貼り付け]

--- 提案資料の構成ルール ---
1. スライド枚数: 7〜10 枚
2. 各スライドのタイトル: 短く・結論先行
3. 各スライドの本文: 3〜5 行・箇条書きベース
4. 案件主の業界用語を使う(汎用ビジネス用語は避ける)
5. 数字 / 具体的な事例 / Before/After を最低 3 箇所入れる

--- スライド構成 ---
1. 表紙: 提案タイトル + 提案者名
2. 課題認識: 案件主の困りごと(案件詳細から推測)
3. 提案概要: 1 文で
4. アプローチ: 3 つのステップ
5. 期待される効果: Before/After
6. 実行スケジュール: 週次 or 月次
7. 体制・想定報酬: シンプルに
8. リスクと対策(オプション)
9. 質問・確認事項(オプション)
10. 次のアクション: 案件主が次に何をすべきか

各スライドの「タイトル」「本文(3〜5 行の箇条書き)」「補足ノート(口頭で話す内容)」を出力してください。

このプロンプトの設計

・ 「7〜10 枚」と明示(枚数指定がないと Claude は 15 枚以上の長大な資料を作りがち)

・ 「業界用語を使う」と明示(汎用ビジネス用語だらけの資料は案件主に刺さらない)

・ 「補足ノート(口頭で話す内容)」を出させる(スライドに書ききれない説明を別フィールドで出してくれる)

・ スライド構成を全部明示(Claude に「構成考えて」と任せると、毎回構成が変わって統一感ゼロになる)

Claude Design への引き渡し方

Claude Code で生成した提案資料の骨子 + 本文を、そのまま Claude Design に渡す。

渡し方の具体手順:

① Claude Code の出力を全選択コピー

② claude.ai/design を開いて新規プロジェクト作成

③ 「以下の構成でプレゼン資料を作って」と貼り付け

④ Claude Design がスライドを自動生成(約 3 分)

⑤ 出力された PPTX をダウンロード(or Canva 連携)

Claude Design は 2026-04-17 リリースで、Pro / Max / Team / Enterprise プラン全部で使える。サムネ生成も同じツールで完結する。

「前回」というのは、Claude Code 導入前に納品した資料のこと。同じ案件主から「業界用語を使う」プロンプト設計後の納品物が、評価が変わった。

3 ヶ月で踏んだ落とし穴

落とし穴 1: スライド枚数を指定しないと長大化する

工程 2: PR 待ち時間 — 週 3 時間 → 0

GitHub の PR を出してから、クライアントのレビュー待ちで生じる「自分が何もできない時間」が週 3 時間あった。これが Claude Code Desktop の Auto-Verify 機能で、ゼロになった。

圧縮前の状況

WebアプリUI 案件で、毎回起きてた:

① 機能を実装して PR 提出(自分の作業)

② クライアントが PR を見るのを待つ(待ち時間)

③ クライアントから修正指示が来る(レビュー後)

④ 修正して再 PR(自分の作業)

問題は「② 待ち時間」。クライアントが PR を見るのは、その日の夜だったり、翌日だったり、週末を挟んだり。その間、わたしは「いつ通知来るか分からないから、別の案件にも本腰入れられない」状態だった。

待ち時間そのものは長くないけど、「待ってる気分」が作業効率を下げてた。

圧縮後の手順

Claude Code Desktop の Auto-Verify 設定で、PR 提出時に自動で:

① CI/CD のテスト実行を待つ(自動)

② エラーが出たら Claude が自動修正(自動)

③ 修正後、再度テスト実行(自動)

④ テスト通過後、デスクトップ通知でわたしに知らせる(自動)

つまり、わたしが「待つ」必要がなくなった。Claude Code Desktop が裏で全部やってる。

クライアントが PR を見るタイミングは変わらないけど、「自分が何もできない時間」が消えた。その時間で別の案件を進められる。週 3 時間が浮く。

Claude Code Desktop の Auto-Verify 設定

設定ファイル(.claude/settings.json)はこんな感じ。

{
  "autoVerify": {
    "enabled": true,
    "watchPaths": [
      ".github/workflows/*.yml",
      "package.json"
    ],
    "onPRSubmit": [
      "npm test",
      "npm run lint",
      "npm run build"
    ],
    "onTestFailure": "claude-fix-test-error",
    "notifyOnComplete": {
      "desktop": true,
      "sound": true
    }
  }
}

この設定の解説

・ watchPaths: 監視するファイルパス(.github/workflows と package.json の変更を検知)

・ onPRSubmit: PR 提出時に自動実行するコマンド(テスト・リント・ビルドを順次実行)

・ onTestFailure: テスト失敗時のアクション(claude-fix-test-error スクリプトを実行 = Claude が自動修正)

・ notifyOnComplete: 完了時のデスクトップ通知(音も鳴らす)

これを 1 度設定すれば、以降の PR は全部このフローで処理される。

GitHub Actions との連携

Claude Code 単体じゃなく、GitHub Actions と連携させると、PR 提出時に GitHub 側でも自動チェックが走る。設定ファイル(.github/workflows/auto-verify.yml):

name: Auto Verify on PR

on:
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test
      - run: npm run lint
      - run: npm run build
      - name: Notify Claude on failure
        if: failure()
        run: echo "Failed - Claude Code will auto-fix locally"

投稿前チェックリスト自動化

#!/bin/bash
# .claude/skills/article-check/check.sh

FILE=$1

echo "=== 投稿前チェック ==="
echo "# 1. 文字数:"
sed 's/<[^>]*>//g' "$FILE" | wc -m

echo "# 2. 禁止フレーズ検出:"
grep -nE 'と言えるでしょう|ではないでしょうか|ぜひ|いかがでしたか' "$FILE" || echo "  (なし)"

echo "# 3. 括弧多用検出:"
grep -oE '（[^）]{1,40}）' "$FILE" | wc -l

echo "# 4. 強調太字密度:"
TOTAL=$(sed 's/<[^>]*>//g' "$FILE" | wc -m)
STRONG=$(grep -oE '' "$FILE" | wc -l)
echo "  $STRONG / $TOTAL 字 = $(awk "BEGIN {print $STRONG / $TOTAL * 1000}") / 1000字"

工程 5: 承認待ち時間 — 30 分 → 5 分

Claude Code で 1 案件を進めるとき、「このコマンドを実行していい？」の承認待ちが 1 案件あたり 30 分発生してた。Auto Mode を入れたら 5 分になった。83% 圧縮。

圧縮前の状況

Claude Code はデフォルトで、ファイル変更・コマンド実行のたびに「実行してもいいですか？」と聞いてくる。安全だけど、1 案件で 20 〜 30 回くらい聞かれて、毎回承認するのに合計 30 分使ってた。

承認の中身は 9 割「問題ない」もの。残り 1 割が「これは止めた方がいい」もの。だけど 10 割全部に確認するから、時間が消費されてた。

圧縮後の手順

Claude Code Auto Mode + deny rules の組み合わせで:

① 安全なコマンド(npm install / git diff / ファイル読み込み)は自動承認

② 危険なコマンド(rm / git push --force / .env 編集)は deny rules で拒否

③ 中間のコマンド(git commit / ファイル書き換え)は確認

結果、確認回数が 20 〜 30 回 → 3 〜 5 回に減った。確認時間は 5 分。

Auto Mode の設定

.claude/settings.json:

{
  "autoMode": {
    "enabled": true,
    "autoApprovePatterns": [
      "npm install",
      "npm test",
      "git diff",
      "git status",
      "git log",
      "ls",
      "cat",
      "grep",
      "find"
    ],
    "denyRules": [
      "rm -rf",
      "git push --force",
      "git push -f",
      ".env",
      ".env.local",
      "credentials.json"
    ],
    "confirmPatterns": [
      "git commit",
      "git push",
      "writeFile",
      "createFile"
    ]
  }
}

deny rules で守るべき 2 つだけ

deny rules は厳密に書くより、「絶対に止めたいもの」だけに絞った方がいい。わたしの場合は 2 つだけ:

① rm -rf 系 → ファイル削除を Claude にやらせない

② .env / credentials → 秘密情報を Claude に読ませない・書き換えさせない

この 2 つさえ守れば、他のミスは「コミット履歴で巻き戻せる」レベル。心配しすぎて deny rules を 20 個書くと、Auto Mode の意味がなくなる。

タスク別 3 パターンのワークフロー

Auto Mode を使うとき、案件タイプ別に 3 つのワークフローを使い分けてる。

パターン A: 単発タスク(コード書く・修正する)

Auto Mode フル稼働。確認はコミット時のみ。1 案件あたり 5 分の確認時間。

パターン B: 探索タスク(リサーチ・新規ライブラリ調査)

Auto Mode は使うが、確認パターンを増やす(confirmPatterns に WebFetch / npm install を追加)。1 案件 10 分。

パターン C: 納品直前(本番デプロイ・最終確認)

Auto Mode をオフ。1 つずつ目視確認。1 案件 30 分以上かけてOK。

このパターン分けで、確認時間と安全性のバランスが取れる。

ポイント 1: プロンプトの保管がカオスになる

良いプロンプトが見つかるたびに、Notion ・Google Docs ・メモアプリ にバラバラに保管してた。次回使うときに見つからない。

回避策: Claude Code の .claude/skills/ に集約する。スキル名を統一ルールで命名する(動詞 + 対象: proposal-deck / pr-monitor など)。

ポイント 2: 設定ファイルが肥大化する

.claude/settings.json が 300 行を超えると、何の設定がどこにあるか分からなくなる。

回避策: 設定ファイルを機能別に分割する(.claude/settings.json + .claude/auto-mode.json + .claude/plugins.json)。各ファイルを 100 行以内に抑える。

ポイント 3: Auto Mode で詰まる

Auto Mode で進行中に、Claude が判断に詰まって止まることがある。確認しないと進まないが、こっちは別の作業してる。

回避策: PermissionDenied hook を設定して、詰まったタスクを自動でスキップ or リトライさせる。詳細は Claude Code v2.1.89 の hook ドキュメントを参照。

ポイント 4: API 課金が想定外

Auto Mode をフル稼働させてると、Claude Pro($20)の枠を超えて API 課金が走ることがある。月 $40 〜 $60 追加で取られた月もある。

回避策: 月初に「今月の Claude 使用枠」を Notion で管理。1 案件あたりの API トークン消費を概算で見積もって、超えそうなら案件を絞る。

ポイント 5: 圧縮効果を測れてない

圧縮できた気がするけど、数字で測ってないと「気がする」だけで終わる。続けるモチベーションが下がる。

回避策: 毎週金曜の作業終わりに 5 分だけ、「今週の圧縮時間」を Notion に記録する。3 ヶ月続けると、グラフで効果が見える。

他職種への応用

この 5 工程は、エンジニア向けに書いてるように見えるけど、実は他職種でも転用できる。

マーケ職への転用

・ 工程 1(提案資料生成)はそのまま使える。マーケ案件で提案資料を作る場面は多い。

・ 工程 3(note 記事自動化)は「ブログ記事・LP コピー」の生成に転用。

・ 工程 4(プラグイン)は不要。マーケ職にはコード補完が要らない。

ライターへの転用

・ 工程 3 がメイン。記事構成生成 + 文体クローン + 投稿前チェックを全部使う。

・ 工程 1(提案資料生成)は寄稿提案にそのまま使える。

Excel 業務への転用

・ 工程 5(承認待ち圧縮)を Excel マクロ実行に応用。Auto Mode で「マクロ実行 → 結果保存 → 通知」を自動化する。

・ 工程 1 は不要。提案資料を作らない職種。

Notion 構築への転用

・ 工程 3 のスキル化アプローチが効く。Notion 構築の「テンプレ生成プロンプト」をスキル化しておく。

・ 工程 4(プラグイン)は github プラグインだけ有効。Notion API との連携をプラグイン化する。

共通する考え方

職種が変わっても「再現可能な手順を持ってるかどうか」が圧縮の本質。

圧縮工程は、その「再現可能な手順」を Claude Code に乗せるための型なだけ。職種ごとに使う工程は違うけど、考え方は同じ。

同じ場所で詰まってる君へ、3 つだけ置いていく

ここまで読んでくれてありがとう。最後に、時間に飲まれてる君に、3 つだけ置いていきたい。

1. 工程 5(承認待ち圧縮)を、今週中に試してみる。
Auto Mode + deny rules 2 つだけの設定で 10 分で終わる。最初の「圧縮の成功体験」が手に入る。

2. 圧縮できた時間を、Notion か手帳に書き出す。
体感じゃなく、数字で記録する。3 ヶ月続けると、グラフで効果が見える。続ける動機になる。

3. 5 工程のうち、自分の作業時間を一番圧迫してる 1 つだけ選んで、深く掘る。
全部を一気にやろうとすると挫折する。1 工程ずつ、月単位で取り組む。「全部やる」より「1 つを完成させる」方が圧縮効果が大きい。

これだけで、わたしが 3 ヶ月で詰まったあの時間は飛ばせる。動くなら今日から動く方が、来週には景色が変わる。
