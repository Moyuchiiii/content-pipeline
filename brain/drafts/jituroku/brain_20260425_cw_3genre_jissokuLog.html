・ 案件一覧を眺めていても、自分にできる案件がどれかわからない

こんな悩みの背景にあるもの

本やオンライン教材で「クラウドワークスの始め方」「実務での稼ぎ方」みたいな概念は学べる。でも具体的な応募文の現物・受注後の Claude Code への指示プロンプト・実際に納品したコードまで通しで見せている素材は、調べた限りほとんどない。

3 ジャンル並行体制で何が変わるか

3 ジャンルを並行で回せるようになると、収入が安定する以外にも 3 つの変化がある。

・ 応募が減る — リピーターが増えるので、1 ヶ月あたりの新規応募数が減る。応募 50 件 / 月 から 応募 10 〜 15 件 / 月 まで落ちた。応募作業に使う時間がそのまま納品作業に回る

・ 断れる案件が増える — 単価が見合わない案件 / 要件が不明瞭な案件 / 客層が合わない案件を、リスクなく断れるようになる。3 ジャンル分の選択肢があると、無理な案件を取らなくて済む

・ 納期管理が楽になる — データ入力 / Excel / Webアプリで作業時間が違うので、その日の体力・スケジュールに合わせて引く案件を選べる。「今日は授業が長くて 1 時間しか作業時間がない」日はデータ入力、「3 連休で集中作業できる」日は Webアプリ、というように切り替えられる

これら 3 つの変化は、3 ジャンル並行が完成してから初めて見えてくる。1 ジャンルだけで回しているとどれも実感できない部分。

その上で、最初は 1 ジャンルから始める

逆説的だけど、3 ジャンル並行の最終形を目指す場合でも、最初は 1 ジャンル（データ入力）に集中するのが正解。同時に 3 ジャンル習得しようとすると、応募文の使い分け / プロンプトの使い分け / 納品物のパターン把握 が同時並行で走って、どれも中途半端になる。

1 ジャンルで「応募 → 受注 → 納品」のサイクルを 3 件以上回してから、次のジャンルに拡張する。この順番を守ったほうが、結果的に 3 ジャンル並行までの到達期間が短くなる。

3 ジャンルが対象になる理由

クラウドワークスの「業務自動化」カテゴリには、ぱっと見では同じに見える案件がいろいろ混ざっている。応募してみると、求められるアウトプットの種類が違うことに気づく。

違いを言葉にすると 3 つに分かれる。

・ データ入力系 — 既存サイトや既存データの「取り込み」「変換」「整形」がメイン。Webから情報を取ってきて整える系

・ Excel系 — 手元にあるファイル（複数CSV、Excel）を集計してレポート化する系。データの「加工と集計」がメイン

・ Webアプリ系 — UI を作る・既存LPを改修する・管理画面を追加する系。「画面を作る」がメイン

この 3 つはクライアント層も違う。データ入力はマーケや EC 担当が多くて、Excel は経理・営業が多い。Webアプリは Web 制作会社や事業会社の Web 担当が多い。

応募文の書き方も違うし、Claude Code に渡す指示の出し方も違う。だからこの記事は 3 ジャンル別にパートを分けてある。

無い。ただし 3 ジャンル分の応募文・プロンプト・コードを並べて見ることで、案件タイプごとに何が違うかが把握できる。1 ジャンルだけやる予定でも、他ジャンルとの比較は応募文の書き分けに役立つ。

無理ではない。自分が最初に受けた Webアプリ案件のときは React も Next.js も書いたことがなかった。ただし、フレームワーク名や用語の最低限の意味（コンポーネント / props / ルート / API ルート など）はクライアントとの会話で出てくるので、調べながら進める前提になる。Claude Code がある分、用語と概念さえ追えれば実装は通る。

納品物のクオリティはどう担保するか

3 段階のチェックを通している。動作テスト（そもそも動くか）/ エッジケーステスト（データが空・文字化け・ネットワークエラー時の挙動）/ クライアント環境テスト（クライアントの PC でも動くか）。3 段目が一番ハマる。自分の環境で動いてもクライアント環境では動かないパターンが頻発する。最近は仮想環境（venv）ごと納品するか Docker 化して渡すようにしている。

応募文テンプレと Claude Code への指示プロンプトはそのまま使える。ただし媒体ごとに「クライアント層」「単価相場」「応募文の文字数制限」が違うので、テンプレを 100% コピペでは通らない。クラウドワークスの実例を 1 度回してから、別媒体への展開を考えるのが現実的な順番。

クライアントから「AI を使っているか」と聞かれたらどう答えるか

聞かれたら正直に答える。「Claude Code というツールを使ってコード生成と動作確認を効率化しています」と伝える。聞かれない限り、開発手法を自分から説明する必要はない。クライアントが求めているのは「動くもの・期日通り・丁寧な対応」であって、開発手法ではない。AI 活用に対するクライアントの認識（プラス / 中立 / マイナス）はバラツキがあるので、聞かれない限り触れないのが安全。

scraper.py の中身は以下のような構造になった。実コードの一部を抜粋する（クライアント情報に関わる部分は仮の値に置き換えてある）。

"""商品情報スクレイピング処理"""

import time
import urllib.robotparser
from typing import List, Dict
import requests
from bs4 import BeautifulSoup


REQUEST_INTERVAL_SEC = 3
USER_AGENT = "CW-CrawlerBot/1.0"


def check_robots(base_url: str) -> bool:
    """robots.txt をチェックして許可されているかを返す"""
    rp = urllib.robotparser.RobotFileParser()
    rp.set_url(f"{base_url}/robots.txt")
    rp.read()
    return rp.can_fetch(USER_AGENT, base_url)


def fetch_product_list(list_url: str) -> List[Dict[str, str]]:
    """商品一覧ページから商品名・価格・在庫を取得する"""
    if not check_robots(list_url):
        raise RuntimeError("robots.txt が拒否しているため停止します")

    headers = {"User-Agent": USER_AGENT}
    response = requests.get(list_url, headers=headers, timeout=10)
    response.raise_for_status()

    soup = BeautifulSoup(response.text, "html.parser")
    items = []
    for item in soup.select(".product-item"):
        name = item.select_one(".name").get_text(strip=True)
        price = item.select_one(".price").get_text(strip=True)
        stock = item.select_one(".stock").get_text(strip=True)
        items.append({"name": name, "price": price, "stock": stock})
        time.sleep(REQUEST_INTERVAL_SEC)

    return items


def detect_structure_change(items: List[Dict[str, str]]) -> bool:
    """HTML 構造が変わって取得結果が異常になっていないか判定する"""
    if len(items) == 0:
        return True
    if any(not item.get("name") for item in items):
        return True
    return False

このコードは、要件を満たしている部分（robots.txt チェック・リクエスト間隔 3 秒固定・異常検知）と、納品物として最低限必要な部分（型ヒント・例外処理・テスト可能な関数分割）の両方が入っている。「動くだけ」のコードと、「納品できる」コードの差はこのへん。

納品時に詰まったトラブル

このジャンルで自分が踏んだトラブルは大きく 2 つ。

トラブル 1 規約違反コード生成

初期に踏んだやつ。Claude Code に「商品情報をスクレイピングして」と雑に指示したら、robots.txt を無視するコードが生成された。リクエスト間隔も 0.5 秒で、相手のサーバーに負荷をかけまくる仕様だった。

これは納品前に自分でコードレビューして気づいた。気づかずに納品していたら、クライアントの依頼サイトでアクセス禁止になっていた可能性がある。

解決策は「Claude Code への指示プロンプトに必ず robots.txt と利用規約の遵守を入れる」こと。

「robots.txt と利用規約を尊重する」「リクエスト間隔は最低 3 秒空ける」

前述のプロンプトテンプレでこの 2 行を最初に書いているのはこのため。Claude Code はガードレールがない指示には素直に従う性質があるので、人間側で安全側のルールを必ず先に渡す。

トラブル 2 要件抜け納品直前修正

これは Claude Code の問題ではなく、自分のヒアリング不足。「スプレッドシートに転記」とだけ要件を読んで、書き込み方式（上書き / 追記 / 日付別）を確認しないまま実装を進めた。納品直前に「日付別シート分けを想定していた」と言われて、既存のシート構造を全部書き換える羽目になった。

解決策は応募文テンプレ C（質問型）の使い方を覚えること。要件が曖昧な箇所は応募段階で聞いてしまう。受注後に聞くと「ヒアリング不足の人」と判断される。

"""売上 CSV の集計処理"""

from pathlib import Path
from typing import Dict, List
import pandas as pd


def load_csv_files(input_dir: Path) -> Dict[str, pd.DataFrame]:
    """input_dir 配下の CSV をすべて読み込んで店舗別の DataFrame として返す"""
    csv_files = sorted(input_dir.glob("月次売上_*.csv"))
    if not csv_files:
        raise FileNotFoundError(f"{input_dir} に CSV が見つかりません")

    dataframes = {}
    for csv_file in csv_files:
        store_name = csv_file.stem.replace("月次売上_", "")
        df = pd.read_csv(csv_file, encoding="utf-8")
        df = validate_columns(df, csv_file.name)
        dataframes[store_name] = df

    return dataframes


def validate_columns(df: pd.DataFrame, file_name: str) -> pd.DataFrame:
    """期待するカラムが揃っているかチェックする"""
    required = ["日付", "商品名", "数量", "売上"]
    missing = [col for col in required if col not in df.columns]
    if missing:
        raise ValueError(f"{file_name} にカラム {missing} が不足しています")
    df["日付"] = pd.to_datetime(df["日付"])
    return df


def aggregate_by_store(dataframes: Dict[str, pd.DataFrame]) -> pd.DataFrame:
    """店舗別の合計売上を集計する"""
    rows = []
    for store_name, df in dataframes.items():
        rows.append({
            "店舗": store_name,
            "合計売上": df["売上"].sum(),
            "合計数量": df["数量"].sum(),
            "取扱商品数": df["商品名"].nunique(),
        })
    return pd.DataFrame(rows)


def aggregate_by_month(dataframes: Dict[str, pd.DataFrame]) -> pd.DataFrame:
    """月別の合計売上を集計する（全店舗合算）"""
    all_df = pd.concat(dataframes.values(), ignore_index=True)
    all_df["年月"] = all_df["日付"].dt.to_period("M")
    return all_df.groupby("年月")["売上"].sum().reset_index()

納品時に詰まったトラブル

Excel ジャンルでは 3 つトラブルを踏んだ。

トラブル 1 文字化け納品

初回納品の Excel が、クライアントの環境で文字化けしていた。原因は CSV の文字コード（Shift_JIS / UTF-8 / UTF-8-BOM のずれ）。日本のクライアントの Excel では Shift_JIS で読み込まれることが多く、UTF-8 で生成すると一部文字が化ける。

解決策はスクリプト側で「日本語環境向けの Excel 出力時は UTF-8-BOM か Shift_JIS で書き出す」を固定にすること。openpyxl で Excel を生成するときは標準で UTF-8 になるけど、CSV 出力を含む場合は明示的に指定する。

トラブル 2 数式の手動再計算が必要

openpyxl で生成した Excel ファイルは、数式セル（=SUM(A1:A10) など）の結果が「ファイルを開くまで計算されない」。クライアントが「ファイルを開いたら数値が表示されない」と連絡してきた。

解決策は Python 側で計算を済ませてから Excel に書き込むこと。「数式を埋め込んで Excel に開かせて計算」ではなく「Python で計算結果を出してから書き込み」に切り替える。

トラブル 3 グラフが画像化されないとレポートにならない

クライアントの一部は「Excel ではなく PDF で報告書として送りたい」というニーズを持っていた。Excel グラフをそのまま PDF 化すると崩れることが多い。

解決策は「matplotlib で PNG 画像を生成 → openpyxl で Excel に画像として埋め込む」フロー。これなら PDF 化したときも崩れない。

Auto Mode の使い方（Webアプリ案件特有）

Auto Mode は Webアプリ案件で一番効く。設計書を渡して「承認が必要な操作以外は自分で進めて」と指示すると、20 分後に基本 UI が完成する。

ただし「何でも承認なしで進めさせる」のは怖いので、deny rules を必ず設定する。

{
  "permissions": {
    "deny": [
      "Bash(git push:*)",
      "Bash(git commit:*)",
      "Bash(rm -rf:*)",
      "Bash(curl https://api.production.*)",
      "Bash(npm publish:*)"
    ]
  }
}

このルールがあれば、Auto Mode が走っているときに本番環境への push / commit / delete / 外部 API 呼び出しが発生しないことが保証される。ローカル環境でのコード生成・ファイル操作だけに絞れる。

具体的な使い方として、以下のフローで案件 H（タスク管理ツール UI）を進めた。

1. 設計書（API エンドポイント一覧 + 画面仕様スケッチ）を Markdown で用意する

2. Claude Code に Markdown を読ませて「Auto Mode で UI 構築をお願いします」と指示

3. コーヒーを飲んで 20 分待つ

4. 戻ってきて生成された UI を確認

5. 修正指示翻訳プロンプトでクライアントの細かいフィードバックを反映

案件 H はこの流れで合計 14 時間で納品まで完了した。Auto Mode を使わず手動で進めると 25 時間以上かかる規模の案件だった。

3 ジャンル横断の学び

学び 1 ジャンル選定の優先順位

3 ジャンルを並行で進めるのが理想だけど、最初から並行は無理。優先順位は データ入力 → Excel → Webアプリ。

データ入力で「応募 → 受注 → 納品」のリズムを掴む。Excel でリピーターを獲得して安定収入の基盤を作る。Webアプリで単価を引き上げる。この順番をスキップすると、Webアプリ案件で要件詰めに失敗して炎上する確率が上がる。

学び 2 応募文の共通パターン

3 ジャンル全体で、通過率の高い応募文には共通する構造がある。

・ 挨拶 1 行（テンプレ感を排除した簡潔な挨拶）

・ クライアントの状況を具体的な数字に置き換える 1 段落（「毎日 30 分の手作業」「月次 5 ファイルの統合」など）

・ 納品物の箇条書き（4 〜 6 項目で具体的に書く）

・ 納期と保証（具体的な日数 + 1 週間保証など）

・ 確認質問 1 〜 2 個（要件曖昧な箇所がある場合のみ）

逆に通過率が低かった応募文の共通パターンは「○○できます」「効率的に」「対応可能です」が並んでいて、クライアントの状況を言語化していないやつ。

学び 3 Claude Code との分業ライン

Claude Code に渡す範囲と、自分でやる範囲の線引きが大事。

・ Claude Code に渡す: コード生成 / テストコード生成 / ドキュメント生成 / 既存コード読解 / 設計案出し

・ 自分でやる: 要件確認 / クライアントとの会話 / 納品前のレビュー / 規約遵守チェック / 実機テスト / トラブル対応の判断

「Claude Code に渡す」を増やすほど作業時間は減る。けど「自分でやる」を減らしすぎると、規約違反コード納品 / 要件抜け納品 / 解釈ずれ実装 などの事故が起きる。

学び 4 単価アップへの道筋

単価を上げる道筋は基本的に 2 つある。

・ 同じジャンルで実績を積んで、リピート受注で交渉する道

・ 新ジャンルに踏み込んで、単価レンジ自体を上げる道

1 つ目の道は安定だけど天井が低い。データ入力で月 ¥150,000 を狙うと、月 7 〜 10 件の受注が必要で、応募数が膨大になる。

2 つ目の道は不安定だけど天井が高い。Webアプリに踏み込んで月 2 件取れれば、それだけで月 ¥130,000 〜 ¥200,000 のゾーンに入る。

3 ジャンル並行が安定するまでの期間として、データ入力で 1 ヶ月、Excel で 1 ヶ月、Webアプリ で 1 ヶ月の合計 3 ヶ月の感覚。これより速く回せる人もいるとは思う。
